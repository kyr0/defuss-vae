# Architecture: tests

Unit tests per module (`test_<module>.py`, mirroring `plugin/scripts/`), shared fixture kits (`vae_testkit.py`; `research_kit.py` and `fixtures/mcp_fixture.py` for the research clients), the dogfood e2e (`e2e.py`) and the browser e2e of the website (`site/`, a bun project). `make verify` runs them all, with coverage at 60 % or more, measured in subprocesses too (`.coveragerc`), since the hook adapter, the CLI and swarm jobs run as their own processes.

## Why this design

Tests use real git repositories, real processes and real files in temporary directories; no mocks or monkeypatching, so a test fails for the reasons a user would. The e2e installs the built release zip into a fresh consumer project and drives only the shipped CLI and hook adapter through the same JSON the harness sends, so it catches a broken payload that source-tree tests cannot see.

The website needs a real browser, because its layout and its component behavior exist only there. `VERIFIED:` during the site's development (2026-10-09) the hero widened the page past a 390 px viewport while `scrollWidth` stayed clean, since the page clips horizontal overflow; the site e2e measures elements against the viewport instead and fails when that bug is put back. The page checks drive the installed Google Chrome through `playwright-core`, so they download no browser.

The site e2e checks a link to a file of this repository in the checkout, because GitHub shows the pushed `main`: fetching it would pass for a file the change deletes and fail for one it adds. `VERIFIED:` on 2026-10-11 GitHub's file pages answered 503 to curl and Bun's `fetch` in bursts for files that exist, while its status page reported no incident. Every other outbound link is opened in CloakBrowser, a Chromium build its makers patch against bot detection, with one retry for a 5xx, 429 or network error. The reason is npm: `VERIFIED:` on 2026-10-11 it answered curl, Bun's `fetch` and headless Chrome with a 403 Cloudflare challenge, and CloakBrowser below 400. `VERIFIED:` on 2026-10-13 a gate run failed because CloakBrowser met the same challenge (403 with `cf-mitigated: challenge`), so a link still challenged after the retry is listed as unchecked: a challenge says nothing about the page, while a 404, any other 403 or a network error still fails. `VERIFIED:` the check, then on Bun's `fetch`, failed on the paper's old address alone, which answered 404 after the paper moved under `/papers/`. LinkedIn links are listed as unchecked, because `VERIFIED:` on 2026-10-11 LinkedIn answered 999 with its login wall for real and made-up profiles alike.

The local gate runs the outbound check; CI does not. GitHub Actions sets `CI=true`, and there the site e2e lists every outbound page as unchecked and `make setup` downloads no CloakBrowser. Elsewhere `make setup` runs `site/install-cloakbrowser.sh`, which downloads the browser and proves it starts. The e2e itself never downloads it: a missing browser fails the check `links.cloakbrowser-installed` with `run make setup`. `VERIFIED:` without the browser the site e2e failed that check alone and left no cache behind; with `CI=true` it passed every check.

## How it works

`RepoCase` creates a temporary git repository per test; `make_python_project` adds a tiny project with its own `.vae/VERIFY.py`, README and ARCH page. The research tests run real servers on 127.0.0.1 (`research_kit.HttpFixture`): an OpenAI-compatible chat server that answers from a script per prompt, in JSON or as server-sent events; an MCP server over streamable HTTP with a session id, paged tool lists and SSE replies; a TypeSafe System One server with a models list, an answer per question type and a 422 `detail` list. `fixtures/mcp_fixture.py` is a real stdio MCP server that prints a banner, pings the client and waits for its answer before replying. A whole research run goes through these fixtures, and its artifacts are checked for every fixture secret. `test_edit.py` checks the edit port against pro-edit's own recorded run of its example article (`fixtures/pro-edit-example/`: parts, review inputs, every memory step byte for byte), ports pro-edit's core tests case by case, runs the engine's pipeline against the chat server (the role of each request read from its prompt) and drives the agent's loop, the second opinion and apply through the CLI. The WebSocket client of `vae_cloak` is tested against a raw-socket RFC 6455 server (masking, a 70 KB fragmented message, ping, close). A real CloakBrowser page read runs only where the browser is installed, so CI skips it. The e2e writes its evidence to `output/e2e.json`; `make bench` reuses it to time the gate cold and cached.

`site/e2e.mjs` serves `docs/` with `Bun.serve` on a free port of 127.0.0.1 and checks the page at desktop width in light and dark and at phone width: clean loading (no console error, failed request or HTTP error), the skip link on the first Tab, in-page anchors and icons that resolve, outbound links that reach their target, each step of the gate demo, the diagram playing to its last step, both scroll scenes showing their six phrases in order, the measurement notes opening, each install tab and copy button, the dark-mode switch across a reload, the phone menu and the scroll-to-top button. It then installs the release zip's CLI into a fresh project under `output/review-e2e/`, reviews a page with two findings and opens the link the CLI prints, as the human does. Each finding marks its text; the human edits a sentence, replies, and comments on a table cell. "Send to agent" saves the response into the review folder, which reads back through the CLI as a `REPLY`, a `NEW` line and exactly one edit hunk, with page lines. The download reads back the same, comments and the edit survive a reload, and the review server stops. It writes `output/site-e2e.json` and screenshots to `output/site/`.

## Operations

- **Resources:** the suite runs in about 40 s plus the e2e, and the site e2e in about 18 s; CI runs them on macOS and Ubuntu, the suite once more on Python 3.9. The site e2e needs Google Chrome installed and `make setup` for its locked dependencies and, outside CI, CloakBrowser's Chromium in `~/.cloakbrowser` (about 200 MB, its README says), whose build the pinned package version fixes.
- **Setup:** on macOS the install script clears the quarantine flag from that cache, since CloakBrowser's README says its macOS build is ad-hoc signed and Gatekeeper may block it; on Linux it installs missing shared libraries through `playwright-core install-deps chromium` (apt-based systems, asks for sudo). It ends by starting the browser, so a broken install fails `make setup`, not the e2e. `VERIFIED:` on macOS the script printed `Chromium 145.0.7632.109` and exited 0; the Linux branch has not run.
- **Reliability:** service tests poll for readiness instead of sleeping, swarm and review tests stop any job or review server still running in `tearDown`, and the e2e service uses a raw socket listener because `VERIFIED:` `http.server` performs a reverse DNS lookup that took more than 30 s on a CI runner. The site e2e needs the network: it fails when the CDN is unreachable or a linked page stays unreachable after one retry.

## Security and privacy

The Python tests run only local commands in temporary directories and use `example.invalid` identities for git. The release check is off in every test and its cache sits in a throwaway folder (`vae_testkit`); `test_update` turns it on against an HTTP server on 127.0.0.1, and the e2e reads a `file://` manifest, so no test reaches GitHub. The research tests reach only their own servers on 127.0.0.1; none calls a real LLM, MCP server or decision endpoint. The site e2e serves `docs/` on 127.0.0.1 only, loads defuss-shadcn from `cdn.jsdelivr.net` as a visitor's browser does (the review page also its pinned Editor.js builds and the icons from `unpkg.com`), and opens each linked page that is not a file of this repository in CloakBrowser, except on LinkedIn and in CI; beyond that and `make setup`, no test needs the network. `make setup` downloads CloakBrowser's Chromium from `cloakbrowser.dev`, and its wrapper checks the archive against a signed checksum list before unpacking it; the Makefile turns off the wrapper's background updates. No personal data.
