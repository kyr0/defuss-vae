# Architecture: gate programs

The CLI (`vae.py`) and the modules behind the hooks: repository facts, static prose checks, the anchored page review and its review page, the verifier, session state, the sub-agent registry, the gate state machine, host adapters and project scaffolding, plus the research engine and its clients for MCP servers, CloakBrowser, OpenAI-compatible LLMs and typed decisions (TypeSafe's System One API). The full verify, review and docs contract is in [`docs/VERIFIER.md`](../../docs/VERIFIER.md).

## Why this design

Modules form a strict layer order and import only lower layers (tested). From the bottom up: `vae_repo`, `vae_net`, `vae_mcp`, `vae_cloak`, `vae_oai`, `vae_decide`, `vae_caps`, `vae_update`, `vae_prose`, `vae_annotate`, `vae_edit`, `vae_verify`, `vae_state`, `vae_swarm`, `vae_gate`, `vae_hooks`, `vae_research`, `vae_project`. The research clients sit low because they need only `vae_repo` and HTTP; each owns the schema of its config pair (`vae_mcp` the servers, `vae_caps` the capabilities, `vae_oai` the LLM, `vae_decide` the typed decisions), and `vae_research` composes them. `vae_edit` owns the review contract (pro-edit's schemas, quotes, memory, run folder) and asks `vae_prose` for the parts, `vae_oai` and `vae_caps` for the engine and its tools, `vae_decide` for the apply check and `vae_annotate` for the review page, which `vae_research` uses for its reports too. Pure checks (`vae_prose`, path classification in `vae_repo`) take text and paths, so tests drive them with real inputs and no mocks; I/O sits in `vae_verify` and above. The Makefile is the only command source: guessing runners per ecosystem would verify commands the project never committed to.

## How it works

`gate()` computes the changed paths since the session baseline, fingerprints the gated ones (code and doc pages), and walks its three steps in order: verify, review, docs. Verify runs the project's `make` verbs and `.vae/VERIFY.py` rules, or only the page checks and rules when nothing but pages changed since the last green suite. Review and docs are JSON attestations keyed to the fingerprint, so any edit reopens the gate.

Session start joins, in priority order, the rules, the gate command, the live sub-agents, MEMORY, CLI_GIST, the defaults of the stacks present ([`references/STACKS.md`](../references/STACKS.md)) and the open episode leads, cut between lines at 9,000 characters with a last line naming what did not fit.

`vae_research` ports the glitcr method: an evidence prompt and a reconciliation prompt each request tools in a `<tool_use_required>` JSON array; the query splits into hypotheses, and closed ones go to the typed-decision endpoint first, with the run's evidence as the content it judges; each open hypothesis gets its own falsification chain (up to 4 in parallel, `--max-rounds` tool rounds each); a final prompt compares the chains. Tools are the capabilities `vae_caps` offers, `experiment` (python3), `decide` and `ask`; a failed tool is a result string the model reads, never an exception. A capability tries its providers in order (an MCP tool, the `cloak` browser or a model of `.env.openai.json` that declares the capability and reads the input as an attachment) and moves on after an exception, an `isError` result or an empty text. `vae_mcp` speaks JSON-RPC over a server's stdin/stdout or over streamable HTTP (session id, SSE replies), answers a server's ping, and serializes calls per server with a lock. `vae_cloak` launches CloakBrowser headless with a throwaway profile and drives it over the DevTools protocol through its own RFC 6455 client.

`vae_edit` ports pro-edit's pipeline (details in [`references/EDIT.md`](../references/EDIT.md)). In the agent's loop each `edit submit` loads the run from disk, checks the findings (strict JSON, the schema subset validator, the quote and evidence rules) and writes one step file, so the loop keeps no process state between parts. An unsure part calls the engine's review once, with corrective retries. The engine is one fresh conversation per call: the prompt plus a transport contract, then tool rounds (`document_read`, `document_grep`, and for the review `file_grep`, `file_read`, `inspect_file`) under turn, tool-call, character, time and token budgets. `edit apply` maps each finding's quote back to the snapshot through its part's offset and replaces from the end of the page backwards. `edit review` checks the agent's revision after the human's response: a word diff of the page against the `base.md` that the first read of the response saved, where every change must lie inside the quote of a note on what asked for it. It then writes the next review folder with the notes as comments. `vae_annotate` fills `templates/annotate.html` with the page, the comments and their metadata as one JSON script (`<` escaped), and reads the human's response back, with text edits as a diff of the editor's Markdown. It also runs the review server: a `ThreadingHTTPServer` on 127.0.0.1 per repository, rooted at `.vae/doc-reviews/`, which a launcher forks off with a new session so it outlives the CLI and leaves no child to reap.

`vae_swarm` keeps one registry entry per live sub-agent. A write takes an `flock` on `tmp/vae/swarm.lock`, replaces the file through `os.replace`, and re-reads it after the settle delay, re-applying a write a racing editor dropped. Liveness comes from one `ps -A -o pid=,ppid=,stat=,lstart=` call: a missing or zombie pid, or one whose process started after the entry did, means the agent is gone. A caller owns an entry when its pid is the caller or an ancestor. `spawn` starts a wrapper (`vae.py swarm run`) in a new session; the wrapper timestamps the job's output into its log, restores its entry every 30 s if an edit dropped it, and records the exit code.

## Operations

- **Configuration and policy:** `.vae/VERIFY.py` (`CONFIG`, `RULES`), loaded fresh on every gate run and hashed into the verification cache key.
- **Complexity and resources:** a cached gate run takes about 90 ms, most of it five `git` subprocesses; `VERIFIED:` (`make bench`, Apple M4, 2026-10-11) archiving each check log before its overwrite and the memory snapshots cost about 15 ms per cold gate run and 10 ms per session start (gate's own share of a cold run 151.5 ms on 0.9.0 against 136.6 ms on 0.8.0; session start 81.6 against 72.0 ms); a cold run adds the project's commands (`timeout_s`, default 180 s each); repository walks stop at 50,000 files, and session start lists files through `git ls-files` instead (20 ms against 135 ms for a walk of 20,000 files); the suites are cached until code or policy change, the page checks until pages or policy change, so a README fix after a green suite reruns only the page checks; with `CONFIG["e2e_paths"]` e2e is cached until a scoped file, a build file or policy changes.
- **Research:** `VERIFIED:` a run on a vLLM endpoint (Qwen3.8, reasoning on, `max_tokens` 32768) with Consensus, z.ai and CloakBrowser took 218 s, 5 LLM calls (79,432 prompt and 37,488 completion tokens) and 8 tool calls (2026-10-11); with `max_tokens` 4000 the reasoning used up every answer, which the run now reports as an empty answer with `finish_reason=length`. Budgets: `--max-tool-calls` (default 24) per run, `--max-rounds` (default 2) per chain, at most 6 chains, 12,000 characters per tool result in a prompt.
- **Edit runs:** the agent's loop costs one CLI call per part plus, for an unsure part, one engine review; `VERIFIED:` (pro-edit's runs) an engine run on a 98 KB report took 5 h 47 min and 23.1 M tokens on a local model, so engine runs start detached and only when the human asks. A run folder is removed by `doctor --tidy` after 14 days untouched.
- **Reliability:** a missing command or metric is `UNKNOWN` and fails; gate text over 9,000 characters is cut to head and tail, with the full text in `gate.txt` in the session's folder; a swarm write is locked, atomic and re-read, and a crashed holder releases its lock.
- **Observability:** each command's output goes to `var/log/vae/<check>.log`, and the previous run's log is gzipped into `var/log/vae/archive/` first (with a `.meta.json`; archives older than 7 days are bundled into one `<YYYY-MM-DD>.tar.gz` per day, never deleted); the gate appends `FAIL`, `DONE` and `FINDING` lines to `.vae/EPISODES.md`; past 100 entries it trims its own oldest `DONE`, `FAIL` and learned `FINDING` lines and never a lead (`LESSON`, `FINDING learn=none`), and `doctor` fails above 30 leads; each spawned job logs to `var/log/swarm/<name>.log`, one ISO-8601-stamped line per output line.

## Security and privacy

Trust boundary: everything in the project is trusted as the user's own code. `VERIFY.py` is imported, Makefile verbs and `command` rules run in a shell, and `swarm spawn` runs the command it is given, like a Makefile verb. `swarm stop` signals only process groups `spawn` created, checked against the wrapper's command line. The registry holds the host name and absolute paths and is gitignored. The hooks' only network request is `vae_update.check`: one GET of the released manifest (2 s timeout), at most daily, run detached so no hook waits on it, cached per user in `$XDG_CACHE_HOME/defuss-vae/update.json`, off with `VAE_UPDATE_CHECK=0`. Research reaches the network only through `vae.py research` and `doctor --repo`, and only the systems a project configures in its `.vae/.env.*.json` files: the LLM and typed-decision endpoints, the MCP servers (stdio servers run as local processes with the environment the config gives them) and CloakBrowser, which opens the pages the model asks for. Secrets live in the gitignored `.vae/.env.<name>` files and reach a request only through `auth_env` or a `${NAME}` in a server entry; client errors replace every secret value with `***`, and a run scrubs them from every artifact, so a server that echoes a header back leaks nothing into `tmp/vae/research/`. Fetched text is data the model reads, so a page can try prompt injection; its reach is the tool catalog, and the only executor is `experiment`, which runs the model's python3 in the run's `experiments/` folder with a 30 s timeout and an environment of `PATH`, `HOME`, `LANG` and `TMPDIR` only. It still runs as the user, with file and network access; `--no-experiments` turns it off. `ask` reaches a human only at a terminal; otherwise the question lands in the report. `swarm status` runs only local `ps`, `vm_stat`, `nvidia-smi`, `docker` or `podman` queries. Memory history (`tmp/vae/memory/`: every version of `MEMORY.md`, `CLI_GIST.md` and `EPISODES.md`, linked newest to oldest through `.meta.json` `prev`) and log archives are never deleted; `doctor --tidy` removes only stale session folders, edit runs untouched for 14 days, interrupted registry writes and dead pid files. State and logs stay in gitignored `tmp/vae/` and `var/log/vae/`, which ignore themselves even before the project's `.gitignore` does. An edit run's engine sends the page, and the repository files and local attachments the model chooses to read, to the configured endpoint; `inspect_file` sends a local file to the capability's provider. With typed decisions configured, the typed-decision endpoint receives the page's first 4,000 characters (its language), each part's text when `editor-thinking` is configured (its complexity), and on `edit apply` each meaning-preserving replacement with its quoted original. It never reads a file git ignores or a `.env*` file, and it fetches nothing external. Its run folder (the page, the findings, traces of every request without headers) is mode 600 in gitignored `tmp/vae/edit/`. A review page loads defuss-shadcn's pinned builds from jsDelivr and the icons from unpkg; the page's text, comments and edits stay in its folder and in the browser's local storage until the human sends or downloads them. The review server listens on 127.0.0.1 only. It answers only paths below its random token and requests whose `Host` names 127.0.0.1 or localhost with its port, and it writes only a review folder's `response.json`, from a POST that carries its own `Origin` and a JSON content type (`references/EDIT.md`). No personal data beyond what the project's own commands print.
